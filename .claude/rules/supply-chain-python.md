# Python Supply Chain Security Rules

Security rules for Python dependency management, integrity verification,
and software bill of materials (SBOM) generation.

**Standards**: OWASP A03:2025 (Supply Chain), NIST SSDF PS.3.1, SLSA Framework

---

## Overview

**Scope**: Python package dependencies, release artefacts, CI dependency
installation, and any file loaded from external or untrusted sources.

**Applicability to this codebase**: Apeirogon Logistics has minimal runtime
dependencies (jsonschema, jsonschema-spec, etc.) but its CI installs from
requirements files. The `generate_release_checksums.py` and
`verify_release_integrity.py` tools implement INT-01. This file extends
that coverage to the dependency and SBOM layers.

---

## SC-01: Pin All Dependencies with Hashes

**Level**: `strict`

**When**: Any Python dependency is declared in `requirements.txt`,
`requirements-dev.txt`, or any other pip requirements file.

**Do**:

```
# requirements.txt -- pin exact version and include SHA-256 hash
jsonschema==4.23.0 \
    --hash=sha256:d71b6a5a9f87a7e1f9e3b6e2ef8c63f8d3f8a8b2e3f8a8b2e3f8a8b2e3f8a8b2

jsonschema-spec==0.2.4 \
    --hash=sha256:e82b6a5a9f87a7e1f9e3b6e2ef8c63f8d3f8a8b2e3f8a8b2e3f8a8b2e3f8a8b3
```

Generate hashes with:
```bash
pip-compile --generate-hashes requirements.in
```

Install with hash enforcement:
```bash
pip install --require-hashes -r requirements.txt
```

**Don't**:

```
jsonschema>=4.0     # VULNERABLE: unpinned -- supply chain attack possible
jsonschema          # VULNERABLE: no version, no hash
```

**Why**: A compromised package version published to PyPI can silently substitute
malicious code at install time. Hash pinning guarantees that only the exact
verified release is installed.

**Refs**: OWASP A03:2025, INT-02 (CLAUDE.md), CWE-829, NIST SSDF PS.3.1

## SC-02: Run pip-audit on Every CI Build

**Level**: `strict`

**When**: CI installs or uses any Python dependency.

**Do**:

```yaml
# In your GitHub Actions workflow:
- name: Audit dependencies for known CVEs
  run: pip-audit --requirement requirements.txt --requirement requirements-dev.txt
```

Locally:
```bash
pip install pip-audit
pip-audit -r requirements.txt
```

**Don't**:

```yaml
# MISSING: installing deps without CVE check
- name: Install dependencies
  run: pip install -r requirements.txt
# No audit step -- a dependency with a known CVE will be silently installed
```

**Why**: `pip-audit` checks installed packages against the OSV (Open Source
Vulnerabilities) database. A dependency with a known RCE or credential-exposure
CVE will be caught before it reaches a running environment.

**Refs**: OWASP A03:2025, NIST SSDF PW.4.1

## SC-03: Generate and Store an SBOM on Every Release

**Level**: `warning`

**When**: Generating a release artefact or release manifest.

**Do**:

```bash
# Generate a CycloneDX SBOM for the release
pip install cyclonedx-bom
cyclonedx-py environment --output-format JSON --outfile release/sbom.json

# Or using pip-licenses for a simple dependency manifest
pip install pip-licenses
pip-licenses --format=json --output-file release/licenses.json
```

Attach `sbom.json` to the release and include its SHA-256 in the release
checksum manifest generated by `generate_release_checksums.py`.

**Don't**:

```
# Releasing without an SBOM means you cannot answer:
# - "Which packages does this release depend on?"
# - "Is this release affected by CVE-2026-XXXXX?"
```

**Why**: An SBOM is the baseline for vulnerability impact analysis. Without one,
you cannot determine whether a new CVE in a transitive dependency affects any
given release version. Required for SLSA Level 2+ compliance.

**Refs**: NIST SSDF PS.3.1, SLSA Framework Level 2, CISA SBOM guidance

## SC-04: Verify Release Artefact Integrity Before Distribution

**Level**: `strict`

**When**: Preparing or consuming any release package, manifest, or export file.

**Note**: This maps to project rule INT-01 (CLAUDE.md). `generate_release_checksums.py`
and `verify_release_integrity.py` implement this control. SC-04 is the supply
chain standard reference for those tools.

**Do**:

```python
# Always verify before loading any release artefact
from tools.lib.common import file_sha256
import hmac

def load_verified_artefact(path: str, manifest: dict) -> dict:
    expected = manifest.get(path)
    if expected is None:
        raise ValueError(f"No checksum in manifest for: {path}")
    actual = file_sha256(path)
    if not hmac.compare_digest(actual, expected):
        raise SecurityError(f"Integrity check failed for release artefact: {path}")
    return json.loads(Path(path).read_text(encoding="utf-8"))
```

**Don't**:

```python
# VULNERABLE: loading release data without integrity check
data = json.load(open("release/scoring_weights.json"))
```

**Refs**: OWASP A03:2025, INT-01 (CLAUDE.md), CWE-829, NIST SSDF PS.3.1

## SC-05: Pin GitHub Actions to Full SHA Commits

**Level**: `strict`

**When**: Adding or updating any GitHub Actions workflow step.

**Do**:

```yaml
# Pin to exact commit SHA -- not a mutable tag
- uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683  # v4.2.2
- uses: actions/setup-python@0b93645e9fea7318ecaed2b359559ac225c90a2b  # v5.3.0
```

**Don't**:

```yaml
- uses: actions/checkout@v4       # VULNERABLE: mutable tag
- uses: actions/checkout@main     # VULNERABLE: branch reference
- uses: actions/checkout          # VULNERABLE: no version at all
```

**Why**: GitHub Action tags are mutable pointers. A maintainer (or an attacker
who has compromised a maintainer account) can move a tag to a different commit,
silently injecting malicious steps into every workflow that references it.
SHA pinning makes the reference immutable.

**Refs**: WARN-04 (CLAUDE.md), OWASP A03:2025, SLSA Framework, OSSF Scorecard

## SC-06: Minimize GITHUB_TOKEN Permissions in Workflows

**Level**: `strict`

**When**: Writing any GitHub Actions workflow file.

**Do**:

```yaml
permissions:
  contents: read   # minimum required for checkout

jobs:
  build:
    permissions:
      contents: read
      # Only escalate where needed, e.g.:
      # security-events: write   # only in SARIF upload jobs
```

**Don't**:

```yaml
# VULNERABLE: omitting permissions block defaults to write-all in some configs
name: CI
on: push
jobs:
  build:
    runs-on: ubuntu-latest
    steps: ...
```

**Why**: A compromised workflow step with write-all token permissions can push
commits, create releases, or modify repository settings. Least-privilege token
scoping contains the blast radius.

**Refs**: WARN-05 (CLAUDE.md), OWASP A03:2025, GitHub security hardening docs

## SC-07: Never Install Dependencies from Untrusted or Unverified Sources

**Level**: `strict`

**When**: Adding any new Python dependency to requirements files.

**Do**:

- Install only from PyPI (the official Python Package Index)
- For internal packages, use a private registry with authentication
- Verify that the package name matches the intended library (typosquatting check)
- Check the package's PyPI page for maintenance status and download count

```bash
# Check for known typosquatting candidates before adding
pip-audit --dry-run <package-name>
# Verify the PyPI page exists and matches the expected maintainer
```

**Don't**:

```bash
# VULNERABLE: installing directly from a GitHub URL without hash
pip install git+https://github.com/unknown/library.git

# VULNERABLE: typosquatted package name (e.g. "requets" instead of "requests")
pip install requets
```

**Why**: Typosquatting and dependency confusion attacks target common
misspellings and internal package names. PyPI does not prevent publication
of packages with names similar to popular libraries.

**Refs**: OWASP A03:2025, CWE-829

## SC-08: Keep a Dependency Update Policy

**Level**: `warning`

**When**: Maintaining the project over time.

**Do**:

```bash
# Check for available updates (without installing)
pip list --outdated

# Use pip-audit to check for CVEs in current deps
pip-audit -r requirements.txt -r requirements-dev.txt

# Update in a branch, re-run full test suite, re-generate hashes before merging
pip-compile --generate-hashes --upgrade requirements.in
python -m pytest developer/tests/
```

Schedule dependency reviews at least monthly, or immediately when a CVE is
published for any direct or transitive dependency.

**Don't**:

```
# Ignoring outdated pinned deps indefinitely -- a pinned dep is not a
# permanent guarantee of security; it is only a snapshot of a known-good state.
```

**Why**: Pinned dependencies resist supply chain attacks but also prevent
security patches from being applied automatically. Regular reviews ensure that
pins are updated to receive CVE fixes in a timely way.

**Refs**: OWASP A03:2025, NIST SSDF PW.4.1

## Quick Reference

| Rule | Level | Risk | Control |
|------|-------|------|---------|
| SC-01 Hash-pinned deps | strict | Tampered package | `--require-hashes` + pip-compile |
| SC-02 pip-audit in CI | strict | Known-CVE dep | `pip-audit` on every build |
| SC-03 SBOM on release | warning | No impact analysis | cyclonedx-bom / pip-licenses |
| SC-04 Artefact integrity | strict | Tampered release | INT-01 tools (existing) |
| SC-05 SHA-pinned Actions | strict | Hijacked CI step | Full commit SHA in uses: |
| SC-06 Minimal token perms | strict | CI token abuse | Explicit permissions: block |
| SC-07 Trusted sources only | strict | Typosquatting | PyPI + hash verification |
| SC-08 Update policy | warning | Stale CVE exposure | Monthly review + re-pin |
