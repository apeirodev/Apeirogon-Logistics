# Release Policy

What constitutes a release, when releases happen, and what guarantees they carry.

---

## Release Scope

A release is a tagged commit with a `RELEASE_MANIFEST.json` and a corresponding `RELEASE_CHECKSUMS.sha256`. Releases are numbered by Star Citizen patch era (e.g. `3.23.0`, `3.24.0`) to make it clear which game patch the scoring config was calibrated for.

Releases are not made on a fixed calendar schedule. A release is made when:

- A new Star Citizen patch changes hauling economics enough to warrant a config update
- A significant tool fix or feature addition is ready
- The scoring config has been calibrated against enough new telemetry to improve accuracy

---

## Release Contents

Every release includes:

- All tools in `tools/`
- `runtime/scoring_config.json` calibrated for the release patch
- `runtime/OCR_normalization_rules.json` with current alias coverage
- Schemas in `schema/`
- Documentation in `docs/`
- `RELEASE_MANIFEST.json` listing included files with SHA-256 hashes
- `RELEASE_CHECKSUMS.sha256` for the manifest itself

---

## Integrity Guarantees

Every release is signed with checksums generated by `tools/generate_release_checksums.py`. Users can verify a release with:

```bash
python tools/verify_release_integrity.py --manifest RELEASE_MANIFEST.json
```

A release that fails integrity verification should not be used. Report it as an issue.

---

## Patch Version Tagging

The release tag matches the Star Citizen patch the scoring config was calibrated for. If multiple scoring config versions exist for the same SC patch, a suffix is used (e.g. `3.23.1` for a mid-patch recalibration). Users are encouraged to record the release tag in their `session_state.json` for telemetry traceability.

---

## No Automatic Updates

Apeirogon Logistics does not phone home or auto-update. Users adopt new releases manually. This is intentional; stability matters more than automatic updates for a calibration-dependent tool.
